# PR #84 — Hero 视觉精度审计与试制

基线：`main fdb79dfcc50e372af0ec1d524156f0638961760e`（2026-10-08）。本轮仅调整 Hero 的表现层素材/渲染，未改规则、AI、地图、HP、碰撞、世界尺寸或 #83 镜头。

## 素材审计

`assets/rmuc/robots` 全部八张 PNG 均具有 RGBA 透明通道。以下按原图尺寸统计，`非透明` 是 alpha>0 的画布像素比例，`实质` 是 alpha>=128 的比例；边框为 alpha>0 的包围盒：

| 素材 | 尺寸 | 非透明 | 实质 | 有效像素包围盒 |
|---|---:|---:|---:|---|
| drone | 1254×1254 | 62.0% | 30.7% | (0,0)–(1248,1254) |
| engineer | 1536×1024 | 37.5% | 36.0% | (0,35)–(1468,1024) |
| hero-chassis | 1536×1024 | 49.4% | 45.3% | (65,8)–(1480,1005) |
| hero-turret | 1662×946 | 38.7% | 37.2% | (0,32)–(1642,946) |
| infantry-chassis | 1430×1100 | 49.6% | 47.6% | (105,3)–(1400,1090) |
| infantry-turret | 1536×1024 | 32.1% | 30.6% | (65,8)–(1522,1024) |
| sentry-chassis | 1536×1024 | 48.2% | 39.5% | (0,10)–(1522,1024) |
| sentry-turret | 1635×962 | 29.9% | 28.7% | (337,37)–(1632,920) |

结构对照参考：[广东工业大学 DynamicX 的 RM2022 Hero 机械开源资料](https://bbs.robomaster.com/article/9116)（仅用于理解真实轮组、开放框架和云台的机械关系，未使用其图片像素、纹理或模型）。

各 Hero 图层的包围盒中心距画布中心均不足原生 20 px（默认渲染尺度约 0.7 px），并非主要错位根因。尺寸 1536/1662 px 不缺采样密度，原图已包含框架、加工板、电机、线束、云台和发射机构；但具体麦克纳姆轮滚子在当前俯视素材中仍难与其他轮组明确区分，不应声称达到 CAD 级还原。

### 问题归因

- **原始素材缺细节**：不是主要问题；但部分轮组形态准确性尚不能仅凭插画证实。
- **细节过密**：是。底盘从 1536×1024 缩到全场 50×34，线性采样降低约 30 倍，微小孔位、螺钉、轮部滚子无法逐项分辨；最大 3.6 倍也仅 180×122。
- **缩放导致损失**：`AssetManager` 已从原图 `smoothscale` 到显示尺寸，并为同尺寸缓存。不存在先小后大的放大链路；常规 LANCZOS 等抗锯齿也不能找回小尺寸丢失的结构。
- **旋转/透明边距**：原来缩放后调用普通 `pygame.transform.rotate`，斜向轮组边缘存在锯齿；Hero 用过滤旋转能改善轮廓。Hero 两图层的透明边距并不构成严重偏移。
- **图层遮挡**：原云台显示 66×38，超过底盘 50×34，遮住大量轮组。3.6 倍、0° 透明像素遮挡测量中底盘可见比例约 28.36%。
- **镜头倍率**：3.6 倍上限仍无法让 1–2 px 的结构达到可辨水平。本轮不修改 #83 镜头。

## Hero 试制改动

1. 复用原 V2 PNG，基于原素材做轻度 gamma=0.83 和原生分辨率非锐化遮罩（radius 1.65、percent 62、threshold 4），透明通道及尺寸不变。没有复制外部受版权约束的照片或引入新素材。
2. 云台显示尺寸从 **66×38** 调整为 **58×29**；底盘保持 **50×34**。相同 3.6 倍截图条件下，底盘露出比例约 **44.18%**，轮组可辨认区域增多。42 mm 炮管仍突出底盘。
3. 仅 Hero 的两张图层采用 `pygame.transform.rotozoom(..., 1.0)` 进行过滤旋转，继续沿用原角度量化与变换缓存；其他机器人与素材加载/回退逻辑不变。
4. LED 仍由游戏对红蓝队伍分别叠加；死亡时不绘制 LED；复活状态继续调用原动画逻辑。世界坐标与真实碰撞不依赖上述呈现尺寸。

## 测试、性能、限制

专项测试核对：RGBA、Hero 过滤旋转缓存、独立旋转、队伍灯光开关及关闭后重新点亮；既有测试覆盖缺失素材回退、世界物理参数不变和桌面资源打包路径。

运行条件：macOS / Pygame 2.6.1 / SDL dummy，`1100×780`、`60 Hz`、`3600 frames`（去掉最初 120 帧）。这是相同环境下的游戏渲染基准，不是实体显示器上的 FPS 结论。

| 指标 | 修改前 | 试制首次 | 完整统计复测 |
|---|---:|---:|---:|
| frame interval p95/p99 | 19/19 ms | 19/19 ms | 19/19 ms |
| frame work p95/p99 | 11/15 ms | 10/14 ms | 10/14 ms |
| render p95/p99 | 3.93/4.56 ms | 3.84/4.21 ms | 3.90/4.30 ms |
| 超过 33 ms | 0 | **1** | 0 |
| 资源变换命中 | 95,417 / 96,132（99.26%） | 95,362 / 96,079（99.25%） | 95,397 / 96,111（99.26%） |
| 资源变换次数 | 715 | 原工具漏记 rotozoom | 714（含 165 次 rotozoom） |
| 缓存驻留内存 | 旧工具未记录 | 77,358,780 bytes | 77,310,928 bytes（约 73.7 MiB） |

第一次试制测试出现 1 次 >33ms 帧间隔尖峰（37ms），完整统计复测未复现；不能将其无依据地归因于素材变更，也不得从验收数据中删除。主分位数未出现持续回退。缓存内存是 `AssetManager` 三组 resident surface 的 `pitch × height` 估算值，不包含 Python 字典及 SDL 其他缓存开销。

**验收边界**：这一试制提高了轮组露出比例与旋转清晰度，但不可能在 50×34 的全场尺寸里显示原图的微细机械结构。请按上面的真实截图和 GIF 判断视觉改善是否足够；未经人工确认不合并。
